# Ops Analytics Copilot

Ask questions about operations data in plain English. The copilot writes a
**read-only** SQL query, runs it against a warehouse database, explains the
answer, and draws a chart, while always showing the SQL it used.

> *"Which category has the most backordered orders?"* → SQL → **Electronics, 120 backorders** → bar chart

## Why I built it

I work in warehouse operations. Managers constantly need answers from
operational data (stockouts, backorders, order volumes) but most can't write
SQL, and giving an AI model write access to a real database is a serious risk.
This tool closes that gap safely: plain English in, verified read-only SQL out,
with the query visible so the answer can be checked.

## How it works

```
question → schema + allowed values → LLM proposes SQL → guardrail → read-only DB → LLM explains → chart
```

1. **Schema introspection.** The app reads the live database schema, plus the exact allowed values of short text columns (for example `status: 'Fulfilled', 'Backordered', 'Cancelled'`), and gives them to the model.
2. **SQL generation.** The model returns one `SELECT` query as text. It never touches the database.
3. **Guardrail.** Before anything runs, `is_safe()` checks the query is a single statement, starts with `SELECT`/`WITH`, and contains no write or schema keywords (`INSERT`, `DELETE`, `DROP`, `PRAGMA`, `ATTACH`, ...). Anything else is blocked.
4. **Read-only execution.** Approved queries run on a connection opened in read-only mode, a second safety layer.
5. **Explanation.** The model summarizes the returned rows in 2–4 sentences and is told not to invent numbers.
6. **Visualization.** The app picks a chart for the result shape: bar for comparisons, pie for small part-to-whole results, line for trends over time. The result table can be downloaded as CSV.

## Design decisions

- **The model never has database access.** It proposes text; the code decides what runs.
- **Two independent safety layers.** A keyword guardrail before execution, and a read-only connection during it.
- **Visible SQL.** Users can verify every answer instead of trusting a black box.
- **Provider-agnostic wrapper.** `src/llm.py` hides the provider, so Gemini can be swapped for Groq without touching app logic.

## Testing and a bug I found

Guardrail unit tests (no API key needed):

```bash
python -m pytest tests/
```

They check that read-only queries pass, that writes, `PRAGMA`, `ATTACH` and
multi-statement queries are blocked, and that the database connection itself
refuses writes.

**Value hallucination.** In early testing, *"which category has the most
backordered orders?"* returned no rows. The model had guessed the status value
as `'backordered'`, but the data stores `'Backordered'`, and SQLite string
comparison is case-sensitive. I fixed it by adding each short text column's
real values to the schema sent to the model. See [`eval/test_questions.md`](eval/test_questions.md)
for the full evaluation and known limitations.

## Tech stack

Python · SQLite · Streamlit · Altair · Google Gemini (`google-genai`) or Groq · pandas

## Run locally

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env              # then add your free Gemini key
python src/build_db.py            # builds data/operations.db
python -m streamlit run app.py
```

## The data

Synthetic but realistic operations data generated by `src/build_db.py`
(seeded, so it's reproducible): 120 products in 6 categories, 4 GTA
distribution centres, 480 inventory records and 4,000 orders from 2025.
Patterns are planted so the analysis has real signal to find:

- Electronics orders are backordered far more often than other categories.
- Barrie-DC runs understocked, with the most items below reorder point.
- Ordered quantity jumps in November and December (larger orders, not more of them).
